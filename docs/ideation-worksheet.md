# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** 돌봄 공백 미리보기（가칭）

**선정 승인:** 사용자가 2026-10-28 “PRD 대상으로 확정하고 싶음”이라고 명시함.

**확정된 방향:** 서울 전체를 대상으로 실제 돌봄SOS 동행지원 안내를 활용하여 필수 외출 동행의 공백 확인과 상담 준비를 돕는다. 병원뿐 아니라 약국·관공서 등 필수 외출을 포함한다. 실제 기관 API 대신 가상 이용자의 돌봄 이력·지원 일정을 반환하는 모의 API를 사용한다. 자치구별 세부 안내의 제공 범위와 문의처 연결 방식은 [미결정]이다.

**한 문장 설명（상세 범위 확인 중）:**

> 서울시민의 필수 외출 동행 필요 상황과 시간을 입력하면, 서비스는 가상 지원 일정의 조회·검증을 거쳐 동행 공백을 확인하고 돌봄SOS 동행지원의 안내 조건과 대조하여 상담 준비표를 반환한다.

**주요 사용자:** [미결정] 초기 사례는 부모님의 돌봄을 준비하는 가족·보호자이며, 이들을 MVP의 주요 사용자로 확정할지는 추가 확인한다.

**정상 실행 흐름:**

```text
사용자의 필요 상황·시간 및 가족 지원 가능시간 입력
→ 가상 이용자의 기존 지원 일정 조회
→ 일정 데이터 유효성 확인
→ 같은 도움 종류의 확정 일정과 비교하여 공백 계산
→ 실제 공공서비스 안내 조건 대조
→ 일치 조건·추가 확인사항·문의처를 담은 상담 준비표
```

이미지와 초기 아이디어에 제시된 흐름이다. 도움 종류는 필수 외출 동행으로 확정되었다. 일정의 확정 기준과 부분 공백 계산 규칙은 [미결정]이다.

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 가상 돌봄 일정 API | 가상 이용자의 돌봄 이력과 기존 지원 일정 조회 | 일정과 공백을 신뢰성 있게 판단할 수 없음 | 모의 API 사용 확정 |
| 실제 사업 안내 자료 | 제공 내용·대상·운영시간·신청방법·문의처의 근거 | 조건 대조와 상담 안내의 근거를 확보할 수 없음 | 실제 공개 자료 사용. API·파일·공식 웹 안내 중 취득 방식은 [미결정] |

**자료 확인 근거（2026-10-28 확인）:**

- [서울복지포털 서비스별 세부내용](https://wis.seoul.go.kr/wfs/sos/contents.do): 동행지원은 병원에 한정되지 않으며 약국·관공서·은행 등 필수 외출 활동의 이동지원과 업무보조를 포함한다.
- [서울시복지재단 돌봄SOS](https://welfare.seoul.kr/web/contents/business1-3-7.do): 일시재가·단기시설·동행지원·주거편의·식사배달 및 돌봄매니저를 통한 제공 절차를 안내한다.
- [도봉구 돌봄SOS](https://www.dobong.go.kr/Contents.asp?code=10010399): 지원요건과 동주민센터 상담·신청 경로를 안내한다.

이 자료의 확인은 공개 API나 기계 판독용 데이터셋 확보를 의미하지 않는다. 교육과정에서 인정하는 공공데이터의 형식과 이용 조건은 [미결정]이다. 서로 다른 자료의 조건이 충돌하면 임의로 결합하지 않고 확인 필요 사항으로 남기는 방식을 제안한다.

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 일정 조회에 실패하면 공백 확인과 상담 준비가 지연된다.
- 조회 실패를 일정 없음으로 처리하면 존재하지 않는 공백을 안내할 수 있다. 이 오판 방지가 초기 아이디어의 핵심 요구이다.

### 운영 영향

- 자동 재시도로 해결되지 않는 장애는 원인 확인과 수동 대응이 필요하다.
- 현재 실제 운영조직과 대응 방식은 [미결정]이다.

### 데이터·비용·보안 영향

- 가상 이용자의 이력과 일정만 사용한다. 실제 기관의 개인 이력을 연계하지 않는다.
- 실제 예약이나 인력 배정은 초기 범위에서 제외한다.
- AWS 사용 의향이 있으나 비용 한도와 배포 규모는 [미결정]이다. 오늘 배포 구성은 작성하지 않는다.

**심각도:** [미결정] 상담 준비 지연·오판 위험을 고려하여 실습 기준 중간을 제안한다.

## 1.3 현재 사람은 장애를 어떻게 발견하고 복구하는가?

팀이 자동화하고 싶은 대응은 API 오류 시 재시도 또는 중단된 서비스 재시작이다. 실제 운영 경험과 단계별 소요시간은 확인되지 않았다.

**승인된 가상 비교 사례:** 일정 API 오류를 서비스 운영자가 직접 확인하고 다시 조회한 뒤 결과를 검증하고 멈춘 작업을 이어가는 과정을 사용한다. 사용자가 채택을 승인했으며 실제 운영 경험이나 측정 성과로 기록하지 않는다.

| 단계 | 현재 사람의 행동 | 사용하는 정보·도구 | 소요시간 | 문제점 |
|---|---|---|---|---|
| 탐지 | 가상 사례: 조회 오류를 보고 알아챔 | 오류 표시·응답 | 미측정 | 직접 확인 전까지 지연될 수 있음 |
| 진단 | 가상 사례: 응답 코드와 오류 내용을 확인함 | 조회 결과·오류 기록 | 미측정 | 매번 직접 구분해야 함 |
| 복구 | 가상 사례: 기다렸다가 같은 조건으로 다시 조회함 | 모의 일정 조회 | 미측정 | 횟수·대기를 사람이 관리해야 함 |
| 검증 | 가상 사례: 대상자·기간·일정 내용을 확인함 | 요청 조건·응답·버전 | 미측정 | 성공 응답만으로 정상 데이터인지 알 수 없음 |
| 보고 | 가상 사례: 작업을 이어가고 결과를 기록함 | 작업 상태·사건 요약 | 미측정 | 재개·기록을 수동으로 수행함 |

**자동화하려는 단계:** 모의 API 오류 감지 → 제한 재시도 → 정상 데이터 검증 → 중단 지점부터 재개.

**사람이 계속 담당해야 할 단계:** 초기 아이디어에서 최종 자격과 실제 배정은 기관 확인 영역이다. 반복 실패·원인 불명 장애의 운영자 확인 절차는 [미결정]이다.

## 1.4 3일 동안 재현 가능한 최소 서비스는 무엇인가?

### 포함 범위

- 실제 공공서비스 안내와 가상 이용자 일정의 구분.
- 돌봄 공백 확인, 사업 조건 대조, 상담 준비표 제공.
- 처음 두 번 503 오류 후 정상 응답하는 모의 일정 API 시연.
- 정상 데이터 검증 후 작업 재개와 조회 실패의 오판 방지.
- 서울 전체의 필수 외출 동행 수요. 병원에만 한정하지 않으며 돌봄SOS 동행지원을 대상으로 한다.

### 제외 범위

- 실제 예약과 인력 배정.
- 실제 이용자의 돌봄 이력과 기관의 개인 일정 API 연계.
- 오늘의 작업목록·코드·테스트·배포 파일 작성, 패키지 설치, 서버 실행, 장애 주입, Git 커밋.

### 사용할 환경

- 사용 가능한 기술·환경: Python, FastAPI, 개인 노트북, Docker, Nginx.
- AWS 배포 의향이 있음. 모든 기술의 필수 사용 여부와 세부 구성은 [미결정].
- 팀: 4명. 재직 개발 경험자 1명, 나머지 3명은 수업에서 다룬 내용을 활용.
- 모의 API 구현 경험: 없음.
- LLM 사용 여부·에이전트 수·필수 프레임워크: 교육과정 확인 필요.

### 선택한 장애 유형

- 확정된 초기 시연: HTTP 503 두 번 후 정상 응답.
- [미결정] 추가 장애로 응답 타임아웃과 응답 형식·필수 항목 오류를 제안함. 최소 세 가지 장애의 최종 조합은 확인 필요.
- [미결정] 프로세스 재시작을 MVP에 포함할지 여부. 관심 사례이며 확정 요구는 아님.

### 지역·서비스 범위

- 대상 지역: 서울 전체. 도봉구에 한정하지 않음（사용자 확인）.
- 서비스 유형: 필수 외출 동행. 병원·약국·관공서 등 외출 목적을 포함（사용자 확인）.
- 여러 돌봄 유형을 함께 비교하는 범위는 현재 선정에 포함하지 않음.
- [미결정] 서울시 공통 사업 안내와 자치구별 세부 안내의 구분, 문의처 연결 방식.
- 범위 제안: 공통 조건 대조와 관할 상담 경로 안내에 집중하고 자치구별 실시간 인력·예약 현황 조회는 추가하지 않는다. 이는 세부 범위 제안이며 확정 요건과 구분한다.

# 2. 에이전트 설계

아래는 초기 이미지의 역할과 PRD에서 검토할 책임을 정리한 것이다. 별도 LLM 에이전트로 구현할 범위는 [미결정]이며, 모든 역할을 독립 에이전트로 나눌 것을 확정하지 않는다.

## 2.1 장애를 탐지하는 주체는 누구인가?

**이름:** [미결정] 장애 탐지 역할.

**관찰 데이터:** 초기 이미지에는 오류 코드·응답시간·필수 항목 검사가 제시되어 있다.

**장애 판정 조건:** 503은 실패로 식별한다. 타임아웃·응답 유효성의 구체적인 기준은 [미결정].

**출력 메시지:** [미결정] 작업 식별자, 실패 단계, 오류 종류와 근거를 전달하는 방식을 제안한다.

## 2.2 원인을 진단하는 주체는 누구인가?

**이름·입력·권한:** [미결정]. 오류 응답과 조회 결과를 근거로 일시적 통신 실패와 데이터 오류를 구분하는 역할을 제안한다.

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| HTTP 503 | 모의 일정 API의 일시적 실패 | 실제 응답 코드 | 초기 시연에서 확인할 오류 |
| [미결정] | 응답 타임아웃 후보 | 응답시간 초과 | 제한시간 [미결정] |
| [미결정] | 응답 형식·필수 항목 오류 후보 | 일정 데이터 검사 결과 | 유효성 기준 [미결정] |

**원인을 판단할 수 없을 때 행동:** 자동 변경 없이 판단을 보류하고 사람에게 근거를 전달하는 방식을 제안한다. 구체적 절차는 [미결정].

## 2.3 복구를 실행하는 주체는 누구인가?

**이름:** [미결정] 복구 역할.

**허용된 복구 행동:** 초기 아이디어의 제한 재시도·재조회. 상한·대기시간은 [미결정].

**금지 행동（가이드 제약）:** 임의 쉘 명령 자동 실행, 운영 데이터 변경·삭제, 인증정보 변경, 허용목록 밖 재시작, 비용 제한 없는 리소스 생성.

**필요한 도구·API·명령:** 모의 일정 조회를 대상으로 하며 구체적인 도구·명령은 PRD 단계에서 확정하지 않는다.

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**이름:** [미결정] 독립 검증 역할.

**독립성이 필요한 이유:** 복구 역할의 성공 보고나 HTTP 성공 응답만으로 정상 일정과 상담 결과를 보장할 수 없다.

**초기 이미지의 검증 항목:** 일정 유효성 확인, 공백·사업 조건 재검사, 중복·과거 결과 차단.

**추가 제안:** 대상자·조회 기간·일정 버전 확인 후 재개하고, 버전이 달라지면 영향을 받는 계산부터 다시 수행한다. 구체적 기준은 [미결정].

**복구 실패 판정 조건:** [미결정] 재시도 상한 도달 또는 유효하지 않은 데이터가 지속되면 실패로 판정하는 방식을 제안한다.

## 2.5 오케스트레이터가 필요한가?

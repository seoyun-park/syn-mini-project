## 2. 프로젝트 개요

**한 문장 정의:** 보호자·복지 담당자가 서울시 거주 만 65세 이상 독거노인을 대신하여 필수 외출 동행 필요 상황과 시간을 입력하면, 서비스는 가상 지원 일정을 조회·검증하여 동행 공백을 확인하고 돌봄SOS 동행지원의 안내 조건과 대조하여 근거·추가 확인사항·문의처를 담은 상담 준비표를 제공한다.

확정된 타깃은 서울 전체에 거주하며 혼자 생활하는 만 65세 이상 노인이고 도움 종류는 필수 외출 동행이다. 병원에 한정하지 않고 약국·관공서 등 필수 외출을 다룬다. 실제 사업 안내와 가상 독거노인의 이력·일정을 결합하되, 실제 이용자의 이력이나 기관 개인 일정 API는 연결하지 않는다. 실제 신청·예약·인력 배정은 수행하지 않는다.

돌봄의 수혜 대상은 독거노인이고 화면을 조작하는 주요 이용자는 보호자·복지 담당자이다. 대리 이용자가 있다는 사실만으로 그 사람이 외출 동행까지 할 수 있다고 판단하지 않는다. 가족·보호자가 없는 경우에도 복지 담당자의 대리 이용을 다룬다. ‘독거’라는 사실만으로 도움을 줄 사람이 없거나 돌봄SOS의 실제 지원 자격을 충족한다고 추정하지 않는다. 프로젝트 타깃과 공공사업의 실제 자격 기준은 별도이다.

핵심 의존 서비스는 가상 돌봄 일정 API이다. 처음 두 번 503을 반환하는 상황에서 자동 감지 → 제한 재시도 → 정상 데이터 독립 검증 → 멈춘 단계부터 재개를 보여준다. 조회 실패를 ‘지원 일정 없음’으로 해석하지 않는 것이 핵심이다.

**사업 근거:** 서울복지포털은 동행지원을 병원·약국·관공서·은행 등 필수 외출의 이동지원과 업무보조로 설명한다. 따라서 병원 이외의 필수 외출도 초기 서비스 유형 안에서 다룰 근거가 있다. [서울복지포털 서비스별 세부내용](https://wis.seoul.go.kr/wfs/sos/contents.do) (2026-10-28 확인)

## 3. 문제 정의

### 3.1 사용자의 문제

서울시 거주 만 65세 이상 독거노인의 필수 외출 동행을 준비하는 보호자·복지 담당자가 기존 지원으로 필요한 시간이 채워지는지, 빈 구간에 어디로 상담할지 확인하는 과정을 돕는다. 복지 담당자의 대리 이용에서는 대상자의 가족 일정·가족 연락처가 없어도 시작할 수 있어야 한다. 따로 거주하는 가족·지인 등의 도움과 기존 공적 지원 일정은 대리 이용자가 확인한 내용만 반영한다.

대리 이용자가 대상자의 지원 일정·조건을 모두 알고 있지는 않을 수 있으므로 ‘없음’과 ‘확인하지 못함’을 구분할 수 있어야 한다. 독거노인에게 직접 화면 조작이나 기술적 장애 해결을 요구하지 않고, 대리 이용자가 대상자에게 설명하거나 기관 상담에 활용할 준비표를 제공한다. 실제 사용자 조사와 수요·사용성 검증은 [미결정]이며 조사 완료로 표현하지 않는다.

일정 데이터 조회 실패를 빈 일정으로 처리하면 실제로 확보된 지원을 누락해 잘못된 공백을 안내할 수 있다. 반대로 오래된 일정으로 계산하면 지원이 확보된 것으로 잘못 안내할 수 있다. 기술 오류가 있는 동안 판단을 유보하고, 유효한 데이터가 확보된 뒤 계산을 재개해야 한다.

### 3.2 서비스 중단 영향

- 독거노인: 동행 공백 확인과 상담 준비가 지연될 수 있고, 잘못된 안내로 지원이 확보되었다고 오인할 위험이 있다.
- 보호자·복지 담당자: 대상자의 입력·일정을 반복 확인해야 하거나 조회 실패를 근거로 잘못된 상담 준비를 할 수 있다. 대리 이용자가 실제 동행 제공자라고 가정하지 않는다.
- 운영자: 오류 확인, 재조회, 응답 검증, 작업 재개를 직접 수행하는 부담.
- 데이터·비용·보안: 가상 정보만 사용한다. 실제 배정·결제는 없으며 AWS의 비용 한도는 [미결정]이다.
- 심각도 제안: 실습 기준 중간. 상담 준비가 지연되거나 오판 위험이 생기지만 실제 돌봄 제공을 제어하지 않는다.

### 3.3 가상의 수동 대응 비교 사례 (사용자 승인)

아래는 서비스 운영자가 일정 API 장애를 처리하는 **비교용 가상 시나리오**이다. 실제 운영 경험이나 측정 사실이 아니다.

| 단계 | 사람이 직접 처리하는 경우 | 자가치유 적용 후 | 비교할 증거 |
|---|---|---|---|
| 탐지 | 조회 실패 표시·응답을 보고 오류를 알아챔 | 실패 응답·시간 초과·유효성 오류를 감지 | 탐지 시각과 오류 근거 |
| 진단 | 응답 코드와 오류 내용을 확인함 | 오류 유형과 재시도 가능 여부를 분류 | 진단 결과와 정책 선택 근거 |
| 복구 | 기다렸다가 같은 조건으로 다시 조회함 | 상한과 대기 규칙을 적용하여 재조회 | 시도 횟수·대기시간·응답 결과 |
| 검증 | 대상자·기간·일정 내용을 확인함 | 복구 실행과 분리된 검증 역할이 확인 | 검증 결과와 사용한 버전 |
| 재개·보고 | 실패한 단계부터 다시 진행하고 결과를 기록함 | 저장된 상태를 확인하여 재개하거나 운영자에게 보류 사유 전달 | 최종 상태·처리시간·중복 여부 |

수동 소요시간은 미측정이다. 실제 비교를 수행하기 전에는 절감 시간이나 개선율을 기재하지 않는다. 향후 비교한다면 같은 가상 입력·사업 자료·장애 조건을 사용하고 사람의 대기시간도 포함한다.

## 4. 사용자와 이해관계자

| 주체 | 필요 | 역할·범위 | 확정 상태 |
|---|---|---|---|
| 서울시 거주 만 65세 이상 독거노인 (핵심 타깃·돌봄 수혜 대상) | 필수 외출의 동행 공백과 상담 준비 지원 | 필요한 외출과 도움 상황의 대상자. 직접 화면 조작을 전제하지 않음 | 사용자 확정 |
| 보호자·복지 담당자 (주요 대리 이용자) | 대상자의 공백 확인·상담 준비를 대신 수행 | 대상자 선택, 확인된 사실·시간 입력, 모르는 정보 표시, 준비표 활용 | 사용자 확정. 대리 이용과 실제 동행 가능 여부는 별도 |
| 실습 운영자 | 복구 과정과 실패 원인을 확인 | 가상 데이터·시연 조건 관리, 보류 사건 확인 | 구체적 담당자 [미결정] |
| 공공서비스 담당 기관 | 필요한 조건과 상황을 상담 과정에서 확인 | 실제 자격·지원 가능 여부·인력 배정 판단 | 서비스 외부. 시스템이 판단을 대체하지 않음 |
| 교육생·검토자 | 요구사항과 복구 증거 평가 | 범위·교육 요건·PRD 검토 | 팀 4명, 검토자 [미결정] |

팀은 재직 개발 경험자 1명과 수업 내용을 활용하는 3명으로 구성되어 있다. Python·FastAPI·개인 노트북·Docker·Nginx 사용이 가능하며 AWS 배포 의향이 있다. 이는 사용 가능 환경이며 전부 필수 사용한다는 의미는 아니다. 모의 API 구현 경험은 없고 LLM·프레임워크 필수 요건은 확인이 필요하다.

## 5. 목표와 성공 기준

수치와 반복 횟수는 모두 **초안 제안**이다. ‘통과’는 이후 실제 검증 증거를 확보했을 때만 표시한다.

| ID | 목표 | 판정 기준 제안 |
|---|---|---|
| G-01 | 조회 상태를 정확히 구분 | 성공한 빈 일정·일정 존재·조회 실패·응답 무효를 구분하고, 실패·무효에서 공백 확정 0건 |
| G-02 | 공백을 정확히 계산 | 완전 공백·부분 공백·전부 지원됨·겹침·경계 인접의 기준 사례 5개에서 예상 구간과 모두 일치 |
| G-03 | 일시 장애 후 완전 복구 | 503·타임아웃·무효 응답 후 정상화의 3종을 각 5회 반복하여 15건 모두 정상 데이터 검증과 작업 재개까지 완료 |
| G-04 | 반복 실패에서 안전하게 중단 | 3종의 지속 실패 사례에서 상한 초과 재시도 0건, 잘못된 상담 결과 완료 0건, 운영자 확인 전환 누락 0건 |
| G-05 | 복구 속도를 관측 | 요청 중 발생하는 모의 장애에서 MTTD 3초 이내, 완전 복구 가능한 사례에서 MTTR 20초 이내를 목표로 기록 |
| G-06 | 결과와 근거를 보존 | 동일 입력·일정 버전·사업 근거 버전에서 정상 실행과 복구 후 공백·조건 판정이 동일하고 최종 준비표 중복 생성 0건 |
| G-07 | 근거 있는 상담 안내 | 각 조건 판정에 근거를 연결하고, 누락 정보는 확인 필요로 표시. 지원 자격·무료 이용·실제 배정 확정 표현 0건 |
| G-08 | 타깃과 실제 지원 자격 구분 | 독거·연령만으로 사업 자격 또는 수발자 부재를 자동 판정하는 사례 0건. 타깃 정보 미확인은 거절이나 자격 불일치와 구분 |
| G-09 | 가족 지원 없는 대상자의 대리 이용 | 복지 담당자가 가족·지인 도움 없는 가상 독거노인을 대신 이용할 때 가족 연락처·계정·일정 요구 없이 공백 확인 가능 |
| G-10 | 대리 이용자와 대상자 구분 | 보호자·복지 담당자 두 유형의 가상 사례에서 조회·계산·준비표가 선택한 대상자의 사례 ID로 연결되고 다른 대상자 정보 혼입 0건 |

수치 목표는 로컬 실습의 작은 가상 데이터와 고정 사업 자료를 전제로 한다. AWS 성능이나 운영 서비스 수준을 보장하는 수치가 아니다. 지속 실패의 안전 중단은 자동 복구 성공률에 포함하지 않고 별도 집계한다.

## 6. 비목표

- 실제 신청 접수·예약·인력 배정·결제·비용 지원 확정.
- 실제 개인정보·건강기록·기관 이용 이력의 수집 또는 연계.
- 필수 외출 동행 외 돌봄 유형의 통합 추천, 서울 외 지역 지원.
- 독거노인 이외 서울시민 전체를 주요 타깃으로 확대하는 것, 독거·연령의 공적 증빙 확인 및 실제 신원 심사.
- 독거노인 본인의 직접 입력 전용 화면, 실제 대리권·위임장 확인 또는 기관 업무시스템·계정 연동 (주요 대리 이용 흐름에 집중하기 위한 초안 제외 제안).
- 상담 준비표 인쇄·파일 저장·외부 공유 기능. 사용자 확인에 따라 이번 MVP는 화면 확인까지 제공한다.
- 자치구별 실시간 인력·예약 현황 연결과 이동 경로 최적화 (초안 제외 제안).
- 사업 정보를 자동 변경하거나 자료 충돌을 임의로 해소하는 동작.
- 임의 명령 실행, 운영 데이터 변경, 인프라 자동 확장.
- 모든 역할의 별도 LLM화, 모델 학습, 고도화된 범용 대화 기능.
- 오늘의 작업목록·코드·테스트·배포 파일 작성·실행 및 커밋.

## 7. 정상 서비스 시나리오

### 7.1 대표 가상 사례

복지 담당자 B가 서울 거주 75세 가상 독거노인 A를 대신해 이용한다. A는 지정한 날짜 10:00~12:00에 관공서 방문 동행이 필요하다. B가 확인한 해당 시간의 가족·지인 도움은 없고, 조회·검증된 A의 기존 동행 일정도 없다. 10:00~12:00 전체를 공백으로 계산한다. A의 가족 계정·연락처·일정을 요구하지 않는다. B가 A의 거동 상태 등 사업 조건을 확인하지 못했다면 해당 조건은 확인 필요로 남긴다. B가 대리 입력했다는 이유로 B의 동행 가능시간을 자동 생성하지 않는다.

비교 사례로, 혼자 거주하더라도 따로 사는 가족이나 지인이 10:00~11:00 동행할 수 있다고 확인한 경우 공백은 11:00~12:00이다. 도움 여부 자체를 모르는 경우는 ‘없음’으로 채우지 않고 해당 구간의 지원 여부 확인 필요로 표시한다. 도움 관계·연령·건강·일정은 모두 실습용 가상 정보이다.

이는 시간 계산 예시이다. 특정 이용자가 사업 대상이거나 해당 외출이 실제 지원 대상으로 확정되었다는 뜻은 아니다. 초기 병원 방문 사례도 같은 흐름으로 제공한다.

### 7.2 처리 흐름 (초안 제안)

1. 대리 이용자가 자신의 역할(보호자·복지 담당자)과 대상 가상 사례를 구분하여 선택한다. 대상자의 서울 내 거주 자치구·만 나이·혼자 거주 여부와 외출 목적·날짜·필요 시간을 확인한다. 가족·지인 도움 여부는 ‘있음·없음·모름’으로 구분하고 있음일 때만 가능 시간을 받는다.
2. 누락·모순은 입력 확인 상태로 돌린다. 서울 외 거주·만 65세 미만·비독거가 명시되면 프로젝트의 현재 타깃 범위 밖으로 안내하며 사업 자체의 자격 불일치와 구분한다. 나이·혼자 거주 여부가 미확인이면 타깃 확인 필요로 표시한다. 모호한 자연어 시간을 임의 확정하지 않는다.
3. 대상자·날짜·조회 기간에 맞는 가상 일정을 조회한다.
4. 응답 상태, 대상자, 조회 범위의 완전성, 일정 버전·확인 시각, 시간 유효성을 검사한다.
5. 같은 도움 종류의 확정 일정과 명시적으로 확인한 가족·지인 지원 가능 구간만 합쳐 필요한 시간에서 제외한다. 도움 없음은 해당 구간을 더 차감하지 않으며, 도움 모름은 미확정 구간으로 남긴다.
6. 공백이 있으면 실제 동행지원 안내 조건을 대조한다. 공백이 없으면 ‘입력·확인된 일정 기준 공백 없음’과 근거를 표시한다.
7. 조건별 일치·불일치·확인 필요, 근거, 추가 질문, 문의 경로를 준비표에 담는다. 공백이 없으면 불필요한 지원 추천을 생략한다.

시간 구간은 시작 포함·종료 제외로 비교하는 방식을 제안한다. 가족·지인 도움과 기존 지원 일정의 중첩은 한 번만 반영하고 미확정 일정은 확정 지원으로 계산하지 않는다. 일부 일정이나 도움 여부가 미확정이면 그 구간은 ‘지원 여부 확인 필요’로 표시하여 전체 공백 확정과 구분한다. 도움 없음이라는 명시적 입력, 도움 여부 미입력, API 조회 실패를 서로 다른 상태로 유지한다. 날짜별 구간만 다루며 반복 일정·자정 넘김·여러 날 연속 동행은 초안에서 제외한다.

### 7.3 상담 준비표

화면의 상담 준비표는 대상 가상 독거노인 표시, 대리 이용자의 역할과 정보 확인 여부, 입력 요약, 확인된 지원·공백 구간, 미확정 구간, 조건별 판정과 이유, 누락 정보·추가 질문, 신청·상담 경로, 출처와 확인일, 적용한 일정·사업 버전을 포함한다. ‘대리 이용자가 확인한 입력과 자료를 기준으로 준비한 상담 참고자료’임을 표시한다. 대상자와 대리 이용자를 혼동하지 않도록 구분하고, ‘도움이 비는 시간’, ‘주민센터에 확인할 내용’처럼 설명하기 쉬운 표현을 사용한다. 전화·방문 상담을 준비할 때 화면에서 확인할 요약을 앞에 둔다. 사용자 확인에 따라 이번 MVP는 화면 확인까지 제공하며 인쇄·파일 저장·외부 공유 기능은 포함하지 않는다. 내부 작업 상태 보존과 사건 로그는 별도 요구이다.

사업 조건은 단순한 일정 공백과 구분한다. 서울복지포털은 일상생활 수행의 어려움, 수발 가능한 가족 상황, 기존 공적 돌봄 이용과 위급상황, 최근 3개월 내 변화라는 네 가지 제공 기준을 안내한다. 각 사실이 불충분하면 자격을 추론하지 않는다. [서울복지포털 서비스 제공 대상기준](https://wis.seoul.go.kr/wfs/sos/service.do) (2026-10-28 확인)

서울 거주·만 65세 이상·독거는 프로젝트 타깃을 설명하는 정보이다. 이 정보가 모두 확인되어도 위 사업 조건을 자동 충족 처리하지 않는다. 특히 ‘독거’와 ‘가족 등이 수발할 수 없음’은 별도로 확인한다. 대리 이용자의 가족 관계나 직무를 대상자 본인의 자격 조건으로 대신 사용하지 않는다.

## 8. 장애 시나리오

F-01은 사용자의 초기 시연으로 확인되었다. F-02~F-04는 최소 세 가지 장애와 실패 경로를 검증하기 위한 **초안 제안**이다. 전부 가상 API에서만 재현하며 오늘 실행하지 않는다.

| ID | 장애 | 위치·신호 | 사용자·운영 영향 | 안전한 재현 방법 | 기대 결과 |
|---|---|---|---|---|---|
| F-01 | 일시적 503 | 일정 API의 503 응답 | 조회·상담 준비 지연 | 해당 가상 작업의 첫 두 조회만 503, 세 번째 정상 | 두 번 재시도 후 독립 검증·재개 |
| F-02 | 응답 타임아웃 | 제한시간 내 미응답 | 진행 대기·작업 중단 | 처음 한 번 제한시간보다 길게 지연하고 이후 정상 | 대기 상한 준수·재조회·검증·재개 |
| F-03 | 정상 코드의 무효 데이터 | 필수 항목 누락·잘못된 시간 | 잘못된 공백 판단 위험 | 처음 한 번 필수 일정 항목 누락, 이후 정상 | 무효 결과 격리·한 번 재조회·검증·재개 |
| F-04 | 동일 장애 지속 | 503·타임아웃·무효 응답 반복 | 상담 판단 불가·운영자 확인 필요 | 별도 사례에서 각 오류를 계속 유지 | 상한에서 중단·회로 차단·판단 보류·사람 확인 |

성공한 빈 일정 응답은 장애가 아니다. 실제 공백, 조건 불일치, 지원 인력 부족은 기술 장애나 자동 복구 대상으로 취급하지 않는다. 근거 자료 부족은 조건 확인 필요로 처리하고 공백 계산 자체의 통신 오류와 구분한다.

독거노인 본인의 화면 조작이나 기술적 장애 해결을 전제하지 않는다. 대리 이용 화면에는 복구 중 ‘대상자의 도움 일정을 다시 확인하고 있어요’, 지속 실패 시 ‘지금은 일정을 확인할 수 없어요. 동행 가능 여부는 아직 알 수 없어요’라고 표시하는 방식을 제안한다. 기술 진단과 복구 승인은 서비스 운영자에게 전달하며, 대리 이용하는 복지 담당자와 기술 복구 승인자를 자동으로 동일인 처리하지 않는다. 지원이 확보되었다는 인상을 주지 않는다.

## 9. 멀티 에이전트 구성

다음은 **논리적 역할의 초안 제안**이다. 모든 역할이 별도 LLM·프로세스일 필요는 없다. 조건 정리·사업 조건 설명에는 LLM 활용을 검토하고, 공백 계산·재시도·검증·상태 전이는 규칙 기반으로 수행할 수 있다. 실제 LLM 수와 프레임워크는 [미결정]이다.

### 조건 정리 역할

- 책임: 대상 독거노인의 지역·연령·혼자 거주 여부·외출 목적·시간과 선택적 가족·지인 도움을 정리한다.
- 입력: 대리 이용자의 역할, 확인한 대상자 정보, 선택한 가상 독거노인 사례.
- 출력: 정리된 조건 또는 추가 확인 질문.
- 사용할 수 있는 정보: 해당 작업의 입력과 지원하는 동행 범위.
- 허용 행동: 누락·모순 표시, 정해진 형식으로 조건 정리.
- 금지 행동: 일정·건강 상태·거주지·자격 사실을 추정하여 채우기. 독거만으로 가족·지인 도움이 없다고 단정하거나 가족 정보를 필수로 요구하기. 대리 이용자의 정보로 대상자의 조건을 대신 채우기.
- 실패 시 행동: 입력 확인 상태로 반환. 후속 일정 판단을 진행하지 않음.

### 사업 조건 대조 역할

- 책임: 공백·사용자 조건과 실제 사업 근거를 대조하고 상담 문구를 작성한다.
- 입력: 검증된 대상 독거노인의 조건·공백 결과·고정된 사업 자료.
- 출력: 조건별 일치·불일치·확인 필요, 이유·근거·질문·상담 경로.
- 사용할 수 있는 정보: 작업에 연결된 사업 근거와 확인된 사용자 조건.
- 허용 행동: 근거가 있는 조건 대조와 설명.
- 금지 행동: 자격·배정 확정, 출처에 없는 조건·연락처 생성. 프로젝트의 독거·연령 기준을 사업의 실제 지원요건으로 바꾸어 설명하기.
- 실패 시 행동: 근거 없는 항목은 확인 필요로 표시하거나 준비표 생성을 보류.

### Monitor

- 책임: 진행 중인 일정 조회의 장애 신호를 관찰하고 사건을 생성한다.
- 입력: 응답 코드·경과시간·데이터 검사 실패 신호.
- 출력: 사건 식별자, 실패 단계, 시각, 관찰 근거.
- 사용할 수 있는 정보: 해당 작업의 조회 상태·오류·시각.
- 허용 행동: 관찰·기록·중복 사건 묶기.
- 금지 행동: 재시도 실행, 설정 변경, 일정 수정.
- 실패 시 행동: 작업을 미확인 상태로 보류하고 운영자에게 관측 실패 전달.

### Diagnosis

- 책임: 증거에 따라 503·타임아웃·무효 응답·알 수 없는 오류를 구분한다.
- 입력: 사건, 응답·검사 근거, 사용 가능한 복구정책.
- 출력: 오류 유형, 진단 이유, 허용된 대응 제안.
- 사용할 수 있는 정보: 해당 사건의 증거와 정책.
- 허용 행동: 분류·근거 설명·정책 제안.
- 금지 행동: 직접 복구 실행, 확인되지 않은 근본 원인 단정.
- 실패 시 행동: 원인 불명으로 분류하고 변경 없이 사람 확인 요청.

### Recovery

- 책임: 허용된 일정 재조회만 제한된 횟수로 수행한다.
- 입력: 사건, 승인된 정책, 남은 시도와 시간.
- 출력: 시도 기록, 응답 또는 실행 실패.
- 사용할 수 있는 정보: 대상 모의 API와 해당 사건의 조회 조건·예산.
- 허용 행동: 정해진 대기 후 같은 조건으로 재조회.
- 금지 행동: 최종 복구 성공 선언, 데이터 수정, 임의 명령·재시작·정책 우회.
- 실패 시 행동: 결과와 사용한 예산을 조정 역할에 전달하고 추가 실행 중단.

### Verification

- 책임: 복구 응답과 후속 결과가 재개·완료 조건을 충족하는지 독립 판정한다.
- 입력: 복구 응답, 최초 요청, 이전 일정 버전, 검사 기준, 후속 계산 결과.
- 출력: 재개 가능·재계산 필요·실패 및 근거.
- 사용할 수 있는 정보: 응답 내용과 작업 조건, 결정적 공백 계산·조건 검사 결과.
- 허용 행동: 대상·기간·필수 항목·버전·시간 검사와 기능 결과 대조.
- 금지 행동: Recovery의 자기보고만으로 통과, 일정 수정·재시도 직접 실행.
- 실패 시 행동: 무효 데이터를 배제하고 재개 차단. 남은 예산이 있어도 허용된 경로로만 재진입.

### Orchestrator

- 책임: 작업 단계·시도 상한·회로 상태·검증·재개·에스컬레이션을 관리한다.
- 입력: 작업 상태, 사건·진단·복구·검증 결과.
- 출력: 다음 역할 호출, 재개·보류·완료·운영자 확인 상태.
- 사용할 수 있는 정보: 해당 작업·의존 서비스의 상태와 고정 정책.
- 허용 행동: 순서 제어, 예산 확인, 상태 저장, 정상 결과 한 번 확정.
- 금지 행동: 재시도 횟수 초기화, 검증 생략, 직접 외부 설정 변경.
- 실패 시 행동: 검증되지 않은 결과를 확정하지 않고 상태 보존·사람 확인.

### Notification

- 책임: 대리 이용자에게 대상자의 진행·보류 상태를 안내하고 서비스 운영자에게 기술 진단·확인 정보를 표시한다.
- 입력: 최종 상태, 근거, 시도·검증 이력, 권장 확인사항.
- 출력: 대상자가 구분되는 대리 이용 안내와 운영자 확인용 사건 요약. 복지 담당자 이용에 가족·보호자 존재를 요구하지 않음.
- 사용할 수 있는 정보: 가상 작업의 비식별 요약.
- 허용 행동: 화면·실습 기록으로 보류·완료 보고.
- 금지 행동: 복구정책 변경, 승인 대행, 외부 메시지 자동 발송.
- 실패 시 행동: 사건 기록에 알림 실패를 남기고 성공 통보 완료로 처리하지 않음.

공백 계산은 별도 판단 에이전트로 두지 않고 검증된 시간 구간에 대한 결정적 계산으로 정의한다. 복구 실행과 검증은 서로 다른 책임으로 유지한다. Orchestrator는 저장된 단계부터 안전하게 재개하고 여러 역할의 상한을 일관되게 적용하기 위해 필요하다.

## 10. 에이전트 협업 흐름

**정상:** 조건 정리 → 작업 상태 저장 → 일정 조회 → 데이터 검증 → 공백 계산 → 사업 조건 대조 → 결과 검사 → 상담 준비표 확정.

**장애:** 조회·검사 실패 → Monitor 사건 생성 → Diagnosis 유형 분류 → Orchestrator 예산·정책 확인 → Recovery 제한 재조회 → Verification 검증 → 재개 또는 보류·운영자 확인.

재조회에서 정상 응답을 받으면 일정 검증을 통과한 뒤 공백 계산부터 이어간다. 이미 입력이 검증되었다면 동일 입력을 다시 받지 않는다. 일정 버전이 달라지면 이전 일정으로 만든 공백·조건 판정·준비표를 무효화하고 영향받는 계산부터 다시 수행한다. 사업 근거 버전이 달라지면 조건 대조부터 다시 수행한다.

작업별 대상 가상 사례·대리 이용자 역할·확인한 입력·진행 단계·일정 버전·사업 근거 버전·사용한 시도 예산을 함께 보존한다. 병렬 응답이나 늦게 도착한 타임아웃 응답은 현재 대상자·작업·시도와 일치할 때만 채택한다. 대상자를 바꾼 경우 이전 대상자의 일정·조건·준비표를 재사용하지 않는다. 최종 결과가 확정된 작업을 재개 요청해도 준비표를 중복 생성하지 않는다.

프로세스·노트북 재시작 후의 영속 재개는 [미결정]이다. 초안의 기본 시연은 실행 중 API 장애에서의 논리적 단계 재개이며, 프로세스 장애까지 복구했다고 주장하지 않는다.

## 11. 장애별 복구정책

이 절의 수치는 **실습용 초안 제안**이다. 사용자 승인·실측 전 확정 정책이 아니다.

### 11.1 시도·시간 상한

- 503·타임아웃: 최초 조회 포함 최대 3회, 추가 재시도 최대 2회. 재시도 전 대기는 각각 1초·2초.
- 무효 응답 단독 사례: 최초 조회 포함 최대 2회. 한 번만 1초 후 재조회하고 무효가 반복되면 중단.
- 혼합 장애: 전체 조회는 최초 포함 최대 3회이고, 무효 응답은 최대 2회 관찰 시 중단한다. 오류 유형 전환·단계 재개로 횟수를 초기화하지 않는다.
- 각 API 요청의 응답 대기 상한은 2초, 사건의 자동 복구·독립 검증 예산은 탐지 시점부터 최대 20초, 전체 작업은 최초 입력 검증 이후 최대 30초.
- 시간 또는 횟수 중 먼저 도달하는 상한을 따른다. 모든 역할은 남은 전체 시간을 넘는 실행을 시작하지 않으며, 종료할 수 없는 외부 호출은 결과를 채택하지 않는다.

근거: 두 번 503 후 세 번째 응답을 확인하는 초기 시연에 필요한 최소 조회는 3회이다. 타임아웃 세 번과 1초·2초 대기는 최대 9초의 조회·대기 시간을 사용하므로 검증·결과 처리 시간을 포함한 20초 목표를 제안한다. 실제 성능은 이후 측정해야 하며, 목표 미달을 성공으로 바꾸지 않는다.

|---|---|---|---|---|---|---|---|---|

| 원인 불명 | 분류 불가·근거 부족 | 대응 정책을 찾을 수 없음 | 자동 변경 없음 | 사람에게 근거 전달 | 추가 자동 시도 0회 | 추가 조치에 필요 | 보류 | 원인과 정책 확인 전 완료 금지 |

### 11.2 회로 차단과 재개

같은 모의 의존 서비스에서 503·타임아웃이 연속 3회 발생하거나, 무효 응답이 2회 반복되면 회로를 연다. 전체 복구시간 예산을 소진해도 자동 처리를 중단한다. 회로가 열린 동안 해당 의존 서비스에 새 자동 조회·복구를 보내지 않고 대기·보류를 표시한다. 자동으로 새 사건을 만들어 예산을 초기화하지 않는다.

회로는 30초 냉각 후 운영자가 명시적으로 허용할 때 한 번의 2초 제한 탐색 조회만 수행한다. 유효한 응답이면 회로를 닫을 수 있고, 실패하면 열린 상태를 유지한다. 운영자 승인이나 탐색은 타임아웃된 원래 작업을 자동 재개하지 않는다. 원래 작업의 입력·버전을 확인한 뒤 별도 재개 승인을 기록하고, 새 실행을 이전 사건과 연결한다. 이 절차는 가상 실습 서비스 안에서만 적용한다.

### 11.3 잘못된 복구와 안전 중단

읽기 중심 복구이므로 외부 일정·사업 데이터를 수정하지 않는다. 변경 전 작업 단계·버전·기존 결과를 보존하고 검증 실패 결과는 최종 결과로 공개하지 않는다. 중간 계산을 무효화하면 마지막으로 검증된 입력 단계로 돌아가되 원래 예산을 유지한다. 임시 결과를 복원한 것만으로 최신 결과라고 표시하지 않는다.

## 12. 자율성과 Human-in-the-loop

| 구분 | 행동 | 선행조건·한계 |
|---|---|---|
| 자동 실행 가능 | 장애 분류·제한 재조회·데이터 검사·계산 재개·사건 기록 | 모의 API와 고정된 정책 안에서만 수행, 검증 통과 필요 |
| 사람 승인 후 실행 | 회로 차단 후 탐색·실패 작업의 새 실행, 실습 복구정책 변경 | 운영자 승인과 이유·시각 기록. 승인 대기 중 자동 실행 금지 |
| 자동 실행 금지 | 임의 쉘 명령, 운영 DB·인증정보 변경, 실제 신청·배정, 허용목록 밖 재시작, 비용 제한 없는 확장 | PRD 승인으로도 자동 허용되지 않음. MVP 복구 수단에서 제외 |

운영 설정·버전 롤백·인프라 변경은 이번 MVP의 복구 행동으로 포함하지 않는다. 서비스 재시작은 팀의 관심 사례지만, 초안에서는 API 오류 복구에 집중하기 위해 제외 제안한다.

사람 확인으로 전환할 때 운영자에게 사건·작업 식별자, 실패 단계, 오류·진단 근거, 누적 시도·대기, 검증 실패 항목, 최종 사용 버전, 권장 확인사항을 제공한다. 기술적 복구의 승인 담당자는 [미결정]이며 독거노인이나 대리 이용자에게 그 책임을 자동으로 넘기지 않는다. 승인 응답 기한은 5분을 제안하며 기한이 지나면 미승인으로 보류를 유지한다. 운영자가 나중에 확인하더라도 묵시적 승인으로 처리하지 않는다. 대리 이용자에게는 대상자의 조회 보류와 이용 가능한 상담 경로를 별도로 안내한다.

## 13. 기능 요구사항

아래 FR은 초안 제안이며 검토 후 확정한다. 인수조건은 이후 검증할 조건이며 현재 통과했다는 의미가 아니다.

### FR-001 외출 동행 조건 정리

- 설명: 보호자·복지 담당자가 대신 입력하는 대상 독거노인의 필수 외출 수요를 정리한다.
- 입력: 대리 이용자 역할, 대상 가상 사례, 대상자의 거주 자치구·만 나이·혼자 거주 여부, 외출 목적·날짜·필요 구간, 가족·지인 도움 있음/없음/모름 및 있을 때의 가능시간.
- 기대 동작: 대상자와 대리 이용자를 구분하고 서울 거주·만 65세 이상·독거의 프로젝트 타깃을 확인한다. 모르는 사실을 추정하지 않고 확정된 입력만 후속 단계에 전달한다.
- 예외 상황: 모호한 날짜·시간 모순은 입력 확인 상태이다. 타깃 정보 미확인과 명시적 타깃 범위 밖을 구분하며 어느 경우도 공공사업 자격 불일치로 단정하지 않는다.
- 인수조건: 만 65세 서울 거주 독거 사례는 타깃에 해당한다. 만 64세·서울 외 거주·비독거 사례는 프로젝트 범위 밖, 나이·독거 미확인은 확인 필요로 표시한다. 복지 담당자 이용에서 가족 도움 없음 입력 시 가족 정보 입력을 강제하지 않는다.

### FR-002 일정 조회 상태 구분

- 설명: 일정 없음과 조회 실패를 구분한다.
- 입력: 대상자·조회 기간과 모의 API 응답.
- 기대 동작: 일정 존재·성공한 빈 일정·조회 실패·응답 무효를 별도 상태로 유지한다.
- 예외 상황: 200 응답이어도 대상·기간·필수 항목이 없으면 무효 응답이다.
- 인수조건: 503·타임아웃·무효 응답 사례에서 ‘일정 없음’ 또는 확정 공백을 표시하는 경우가 0건이다.

### FR-003 일정 유효성 검사

- 설명: 계산에 사용할 수 있는 완전하고 일관된 일정만 채택한다.
- 입력: 요청 조건, 응답의 대상·기간·일정·버전·확인 시각.
- 기대 동작: 대상 일치, 조회 범위 전체 응답 여부, 필수 항목, 시간 구간, 버전을 검사한다.
- 예외 상황: 일부 일정 누락 여부가 불명확하면 빈 일정으로 간주하지 않고 확인 불가로 처리한다.
- 인수조건: 대상·조회 기간 불일치, 필수 정보 누락, 잘못된 시간 구간을 모두 계산 전에 차단한다.

### FR-004 동행 공백 계산

- 설명: 필요한 구간에서 확인된 지원 구간을 제외한다.
- 입력: 대상자의 검증된 동행 확정 일정과 명시적으로 확인한 선택적 가족·지인 도움 구간.
- 기대 동작: 중첩 지원은 합쳐 계산하고 부분 공백과 미확정 지원 구간을 구분한다. 대리 이용자의 존재를 지원 구간으로 바꾸지 않는다.
- 예외 상황: 미확정 일정·도움 모름은 확정 지원으로 차감하지 않고 확인 필요로 남긴다. 가족 정보 미입력과 도움 없음은 다른 상태이다.
- 인수조건: 10~12시 필요·도움 없음·기존 일정 없음이면 전체 10~12시, 10~11시 도움 확인이면 11~12시가 공백이다. 도움 모름은 확정 공백과 구분하며 중첩·인접의 G-02 기준도 충족한다.

### FR-005 사업 조건 대조

- 설명: 돌봄SOS 동행지원의 근거와 확인된 조건을 대조한다.
- 입력: 대리 이용자가 확인한 대상 독거노인의 조건·공백·사업 안내와 버전.
- 기대 동작: 조건별 일치·불일치·확인 필요와 이유를 제공한다.
- 예외 상황: 자료 간 충돌·정보 누락·지역별 차이는 확인 필요로 남긴다. 프로젝트 타깃에 해당하거나 일정 공백이 있다는 사실만으로 자격을 확정하지 않는다.
- 인수조건: 거동 상태를 모르면 확인 필요와 추가 질문을 표시한다. 독거라고 수발자 부재를 자동 충족 처리하지 않고, 대리 이용자의 나이·거주지를 대상자의 조건으로 사용하지 않는다.

### FR-006 상담 준비표 제공

- 설명: 상담에 필요한 상황과 확인사항을 정리한다.
- 입력: 대상 가상 사례, 대리 이용자 역할·확인 상태, 검증된 공백·조건 판정·출처·상담 경로.
- 기대 동작: 7.3절의 항목과 대상자별 상담 요약을 화면에서 제공한다. 대리 이용자의 입력과 기관이 최종 확인할 사항을 구분하며 인쇄·파일 저장·외부 공유 기능은 제공하지 않는다.
- 예외 상황: 조회 실패면 ‘대상자의 일정을 확인할 수 없어 동행 가능 여부를 알 수 없음’을 표시한다. 공백이 없으면 그 결과를 명시하며 가족에게 연락하라고 일률적으로 안내하지 않는다.
- 인수조건: 대상자와 대리 이용자 역할, 근거·확인일·추가 질문·신청 경로가 포함되고 최종 자격·배정 확정 문구가 없다. 가족 없는 복지 담당자 사례에서도 준비표를 완성할 수 있다.

### FR-007 장애 사건 생성·진단

- 설명: 관찰 가능한 근거로 장애와 대응 정책을 연결한다.
- 입력: 오류 코드·경과시간·검사 실패와 작업 상태.
- 기대 동작: 사건 식별자·발생 단계·시각·유형·진단 근거를 기록한다.
- 예외 상황: 알 수 없는 오류는 추측하여 재시도 정책에 넣지 않고 운영자 확인으로 전환한다.
- 인수조건: F-01~F-04에서 오류 근거를 추적할 수 있고 같은 사건의 재시도로 새 예산이 생기지 않는다.

### FR-008 제한 재시도·회로 차단

- 설명: 정책이 허용한 모의 일정 재조회만 수행한다.
- 입력: 사건 유형, 누적 시도, 남은 시간, 회로 상태.
- 기대 동작: 11절의 상한·대기를 적용하고 회로가 열리면 조회를 차단한다.
- 예외 상황: 혼합 장애·새 사용자 요청으로 기존 실패 예산이나 열린 회로를 우회하지 않는다.
- 인수조건: 두 번 503 후 정상 응답을 세 번째 조회에서 받으며, 지속 장애에서는 허용 횟수·시간을 넘는 조회가 없다.

### FR-009 독립 검증과 기능 정상화 판정

- 설명: 재조회 성공과 완전한 작업 복구를 구분한다.
- 입력: 복구 응답, 요청·버전, 공백·조건 대조 결과.
- 기대 동작: Recovery와 분리된 판정으로 데이터 유효성과 후속 기능 조건을 확인한다.
- 예외 상황: HTTP 200이라도 잘못된 대상·시간·버전이면 통과시키지 않는다.
- 인수조건: 유효하지 않은 복구 응답에서 작업 재개 0건. 같은 입력·버전의 정상 실행과 공백·조건 판정이 일치해야 완전 복구이다.

### FR-010 상태 저장과 안전한 재개

- 설명: 입력부터 전부 다시 하지 않고 영향을 받는 단계부터 이어간다.
- 입력: 작업 ID·대상 가상 사례·대리 이용자 역할·진행 단계·입력·버전·시도 예산·검증 결과.
- 기대 동작: 대상자와 검증된 입력을 보존하고 버전 변화에 따라 공백 계산 또는 조건 대조부터 재실행한다. 대상자 변경 시 이전 대상자의 결과를 사용하지 않는다.
- 예외 상황: 상태 누락·작업 불일치면 자동 추정하여 재개하지 않는다. 프로세스 재시작 후 재개는 범위 미결정이다.
- 인수조건: 일정 버전 변경 시 기존 계산을 그대로 사용하지 않으며 늦은 응답이나 반복 재개 요청이 최종 준비표를 중복 생성하지 않는다.

### FR-011 보류·사람 확인·승인 기록

- 설명: 자동 복구가 불가능한 사건을 운영자에게 전달한다.
- 입력: 상한 도달·검증 실패·원인 불명 사건.
- 기대 동작: 판단 보류와 원인·시도·다음 확인사항을 표시하고 필요한 승인 결과를 기록한다.
- 예외 상황: 승인 없음·거절·시간 초과는 보류 유지. 자동 승인으로 간주하지 않는다.
- 인수조건: 지속 장애 3종에서 운영자 확인 정보가 남고, 승인 없이 회로 탐색이나 실패 작업 재실행이 발생하지 않는다.

### FR-012 실제·가상 데이터와 출처 추적

- 설명: 상담 근거와 실습 데이터를 구분하고 판정을 재현한다.
- 입력: 사업 자료·출처 URL·확인일·근거 버전, 가상 사례·일정 버전.
- 기대 동작: 각 결과에서 사용한 자료를 찾을 수 있게 하고 사업 자료 변경 시 영향받는 판정을 갱신한다.
- 예외 상황: 원문 근거가 없거나 상충하면 지원 조건·연락처를 생성하지 않는다.
- 인수조건: 준비표에서 실제 사업 자료와 가상 독거노인 정보를 구분할 수 있고, 대상 사례·대리 이용자 역할·일정·근거 버전으로 판정 내용을 재현할 수 있다.

### FR-013 대리 이용자와 대상자 연결

- 설명: 보호자·복지 담당자의 조작과 돌봄 수혜 대상자의 조건·일정을 구분한다.
- 입력: 대리 이용자의 역할과 선택한 가상 독거노인 사례.
- 기대 동작: 조회·검증·계산·재개·준비표를 같은 대상자와 연결하고 화면에서 누구의 상황을 정리하는지 확인할 수 있게 한다.
- 예외 상황: 대상자를 선택하지 않았거나 응답이 다른 대상자의 것이면 진행을 중단하고 대상자 확인을 요청한다. 실제 인증·대리권 심사는 이번 가상 시연 요구에 포함하지 않는다.
- 인수조건: 보호자와 복지 담당자 두 유형 모두 대상 사례로 작업을 진행할 수 있다. 대리 이용자의 정보나 이전 대상자의 일정·준비표가 선택한 대상자의 결과에 들어가는 경우가 0건이다.

## 15. 데이터와 로그 요구사항

### 15.1 데이터 구분과 취득

| 데이터 | 필요한 정보 수준 | 출처·상태 | 취급 원칙 |
|---|---|---|---|
| 실제 사업 안내 | 사업명·지역·제공 내용·조건·제공 시간·신청 방법·상담 경로 | 서울시 공식 안내 확인됨. 공개 API·파일 확보 및 교육 인정 기준 [미결정] | 출처·확인일·적용 범위·근거 버전 보존 |

| 선택적 비공식 도움 | 가족·지인 도움 있음/없음/모름, 있을 때 확인된 구간 | 가상 입력 | 가족·지인의 존재와 대리 이용자 본인의 동행을 자동 가정하지 않음 |

| 작업 상태 | 대상 사례·대리 이용자 역할·단계·입력 참조·일정 및 근거 버전·누적 시도·최종 결과 참조 | 논리적 저장 방식 제안 | 상세 스키마·저장소·영속성 [미결정] |

3일 범위에서는 소량의 확보된 공식 자료를 출처와 함께 고정해 사용하는 방식을 제안한다. 공개 API·다운로드 파일 사용이 수업 필수라면 해당 요건을 충족하는 자료를 확보한 뒤 취득 방식을 확정해야 한다. 공식 웹 안내를 확인한 것만으로 공공데이터포털 API 연동을 완료했다고 표현하지 않는다.

서울 전체의 만 65세 이상 독거노인을 대상으로 하되 초안은 서울시 공통 안내와 대상자의 거주지 관할 동주민센터 상담 경로를 우선한다. 대리 이용자의 거주지·근무지로 관할을 대체하지 않는다. 주소지 동주민센터에 전화 또는 방문하는 이용 방법은 공식 안내에서 확인된다. 자치구별 연락처 전수 수집·자동 갱신은 별도 범위 결정이 필요하다. [서울시복지재단 돌봄SOS](https://welfare.seoul.kr/web/contents/business1-3-7.do) (2026-10-28 확인)

### 15.2 필수 로그

- 작업·사건·추적 식별자, 대상 가상 사례 참조·대리 이용자 역할과 의존 서비스 식별. 대상자의 나이·독거·건강 정보 전문은 사건 로그에 복사하지 않음.

- 검증 항목별 결과, 최종 상태·소요시간, 이전 사건과 재실행 연결.

시간은 UTC 기준 시각과 경과시간을 기록하고 사용자 화면은 Asia/Seoul로 표시하는 방식을 제안한다. 한 실습 환경에서 경과시간 기준을 일관되게 적용한다. 장애 주입 시각은 이후 실습용 장애 제어에서 기록하며 실제 운영 탐지로 일반화하지 않는다.

로그에 이름·상세 주소·건강 상태의 입력 전문·인증정보를 포함하지 않는다. 출처 링크와 가상 사례 참조만으로 검토할 수 있게 한다. 저장 위치·접근권한·보존기간은 [미결정]이며 임의로 영구 보존하지 않는다.

## 16. 검증 및 완료 기준

### 16.1 판정 상태와 시간

- **데이터 복구:** 일정 응답이 독립 유효성 검사를 통과한 상태. 이것만으로 완전 복구를 선언하지 않는다.
- **완전 복구:** 정상 데이터로 필요한 단계가 재개되고, 공백·조건 판정과 상담 준비표의 필수 항목·근거 검사가 통과한 상태.
- **안전 중단:** 복구하지 못했음을 기록하고 잘못된 공백·자격·배정을 확정하지 않은 채 사람 확인으로 전환한 상태.
- **주입 시각:** 실습 API가 해당 오류 동작을 시작한 시각. 사건과 연결하여 기록한다.
- **탐지 시각:** Monitor가 해당 사건을 처음 식별한 시각.
- **정상화 시각:** 독립 검증이 완전 복구 조건을 통과시킨 시각.
- **결과 확정 시각:** 검증된 준비표가 중복 없이 한 번 확정된 시각. 정상화 이후 공개 지연도 별도로 확인한다.

MTTD는 탐지−주입, MTTR은 정상화−주입, 복구 실행시간은 정상화−복구 시작으로 계산한다. 복구되지 않은 사건은 MTTR 성공 평균에서 제외하고 보류·실패 지속시간과 함께 별도 집계한다. 시간 상한이 끝난 사례를 정상화로 처리하지 않는다.

완전 복구율은 완전 복구 건수÷전체 주입 사건 수로 보고하고 장애 유형별 건수를 함께 표시한다. G-03의 일시 장애 복구율은 별도 부분집합으로 보고하여 지속 실패를 숨기지 않는다. 안전 중단률은 지속 실패 사례 중 안전 중단한 비율, 공백 정확도는 기준 사례 중 기대 구간과 일치한 비율이다. 모든 비율에는 분자·분모를 함께 표시한다.

### 16.3 PRD와 프로젝트 완료의 구분

PRD 완료는 미결정 핵심 사항 해소, 제안 정책·범위 검토, 사용자·검토자의 명시적 승인을 뜻한다. 프로젝트 기능 완료는 이후 별도 단계에서 실행 증거로 판단한다. PRD 작성만으로 복구 성공이나 테스트 통과를 선언하지 않는다.

### 16.4 PRD 자체 검토 결과

- **충족 항목:** 서울시 거주 만 65세 이상 독거노인 타깃과 보호자·복지 담당자의 대리 이용을 개요·문제·이해관계자·사례·입력·공백·상담 준비표·역할·FR·NFR·데이터·검증·MVP에 반영함. 가족 도움 없음/모름과 독거/사업 자격을 분리함. 승인된 가상 수동 비교, 세 가지 장애와 지속 실패, 복구·독립 검증, 상태·버전 재개, 권한·상한·차단·안전 중단도 유지함.
- **보완이 필요한 항목:** 데이터 요건 충족 자료 확보, LLM 교육 요건, 자치구 안내 상세 범위, 정책·목표 수치, 승인 담당자·로그 보존 기준의 확정. 타깃·연령·대리 이용·화면 제공 범위는 사용자 답변으로 해결됨.
- **미결정 사항:** 19절 참조. 상세 요구사항은 검토용 제안이며 사용자 승인으로 위장하지 않음.
- **범위 초과 위험:** 서울 전체의 자치구별 조건·연락처 전수 수집, 실시간 기관 연동, 프로세스 재시작 복구, 모든 역할의 별도 LLM화.
- **승인 권고:** 수정 후 승인. 현재는 최종 승인을 요청하지 않고 핵심 미결정 사항과 제안 범위에 대한 검토를 먼저 진행한다.
- **검증 한계:** 문서 내용 검토만 수행했으며 코드·테스트·서버·배포·장애 실험을 수행하지 않음.

| AWS 비용·운영 범위 확대 | 비용·기간 초과 | 비용 한도·실행 범위는 별도 확인. 자가치유의 자동 확장 제외 |
| 모의 API·다수 LLM 역할 동시 도입 | 팀 경험 대비 복잡도 증가 | 하나의 모의 의존 서비스와 논리적 역할 분리 유지 |

## 19. 미결정 사항

결정 기한은 최종 PRD 승인 전을 기준으로 한다. 외부 요건 미확인 상태에서 최종 승인·구현 진행으로 넘어가지 않는다.

| ID | 미결정 사항 | 필요한 결정 | 결정 책임자 | 결정 기한 |
|---|---|---|---|---|
| D-01 | 공공데이터 인정 기준과 실제 취득 자료 | API·파일 필수 여부, 활용 가능한 데이터·이용 조건, 공식 안내 고정 사용 허용 여부 | 사용자·교육 담당자 확인 | 최종 PRD 승인 전 |
